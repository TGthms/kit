### Deeper audit findings — report only, not fixed in this pass

1. **PDF file-change races (high priority):** `pdf-organize.tsx:48` guards thumbnail completion but writes page count/order before checking the generation. An older 30-page load can replace the order for a newer 40-page file, allowing an export of only 30 pages. `pdf-metadata.tsx:29` has no generation guard, so older metadata can be written onto the newer file. Both reproduced with deferred component-level reads; temporary audit fixtures were removed after verification.
2. **ZIP entries can disappear (high priority):** `convert-tools.tsx:63` and `image-compress.tsx:43` use raw/non-unique entry names, bypassing `uniqueArchiveNames()`. Reproduced two `report.txt` entries becoming one containing only the second file. Compression can also collide after extension conversion. The conversion hub additionally accepts unsupported image/output choices and can put JPEG bytes in a file named `converted.json`.
3. **Numeric inputs can crash/freeze tools:** `text/base.ts:3` accepts a fractional source base before calling `BigInt`; entering `2.5` in Number base reaches the whole-page error boundary (browser-reproduced). `converter/date.ts:122` loops without a useful bound for business-day additions; `1e20` is accepted as an integer but decrementing it by one does not progress. Confirmed in an isolated worker terminated after the audit, without hanging the app.
4. **Unicode PDF text is drawn with the wrong font:** `pdf/core.ts:44` sets a measuring font, then resizes that same canvas before reading `measure.font` again. Resizing resets it; browser reproduction measured `600 108px system-ui` but drew `10px sans-serif`. This affects non-ASCII watermarks, signatures, and page labels, making them much too small inside oversized image bounds.
5. **DST gap conversion silently changes the input:** `converter/timezone.ts:119` maps Los Angeles `2026-03-08T02:30` to an instant whose source time is `01:30`, without rejecting or explaining the nonexistent local time. Gap/fold handling needs an explicit policy and tests.
6. **JSON edge cases return wrong or incomplete output:** `text/json-query.ts:6` collides dotted keys with nested paths and loses reserved `__proto__` keys. `text/json-types.ts:18` rejects an empty key whose value is an object; root arrays omit their array alias; a nested `root` object can capture the exported Root name. Reproduced directly against the engines.
7. **Older tool labels are still disconnected:** e.g. Number base and PDF metadata render sibling `<Label>` / `<Input>` pairs without ids or `htmlFor`. Browser accessibility inspection confirmed unnamed Number base inputs. These should use the existing Field primitive. Timeline/crop/organize workflows also warrant a focused keyboard pass.
8. **Dependency maintenance:** fresh npm audit flags 18 affected packages (1 critical, 13 high, 4 moderate, including propagated flags). This is not evidence of 18 exploitable browser issues. Kit is a static export and does not use the affected `next/og` server endpoint; many flags concern development/server tooling. The locked `smol-toml@1.8.0` parser is reachable in the browser and has a confirmed quadratic parse-time advisory, fixed in 1.9.0: https://github.com/squirrelchat/smol-toml/security/advisories/GHSA-r4xh-jqrq-34v2. Next, Vitest/Vite, sharp, and transitive packages need a compatibility-tested refresh. Liquid Glass's inherited MCP-server flag comes through vgpu tooling, not a Kit MCP server. Dependencies were not changed during this report-only audit.

The most useful structural improvements are shared per-file generation/cleanup helpers, consistent archive naming/output validation, bounded or worker-based expensive text/date operations, and workflow tests for rapid source replacement and exported results. The current large pure-engine test suite does not catch these UI ownership races.

## Current baseline (2026-08-29)

- **94 tools** in `src/lib/tools/registry.ts`.
- Next.js 16 App Router with static export, PWA shell, Cloudflare Pages (canonical) and GitHub Pages CI. GitHub Actions runs typecheck, lint, and tests before the Pages backup publish.
- Cloudflare Pages Free allows 20,000 files per deploy. Next 16 writes extra `__next.*.txt` segment-prefetch files per route (~23k files for 31 locale URLs). `scripts/prune-export.mjs` runs as `postbuild` and deletes those extras, keeping `index.html` and `index.txt` so client navigations still work. Cloudflare clones GitHub and runs `npm run build`; it does not upload the gitignored local `out/` folder.
- 30 first-class locales plus the legacy `/zh/` path alias; localized tool metadata, sitemap, robots, 62 legal documents, and a How Kit works story page at `/{locale}/how/` (honest tables for what crosses the network, what Kit downloads once, the home greeting system, and offline; locale-aware links, never a hardcoded `/en/` path). No fake 0%/100% bars. Legal `/privacy/` stays the policy.
- `/` is an entry point, not a page: it picks a language from the stored choice or the browser and replaces to `/{locale}/`. It therefore names `/{defaultLocale}/` as its canonical, carries no `hreflang` list of its own, and is left out of the sitemap. Listing it would put a forwarding address in front of a search engine as though it were a destination, competing with the home page it forwards to. The document defaults in `src/app/layout.tsx` deliberately set no canonical and no language list, so a page that never states its own — the not-found document in particular — cannot claim the home page as itself. `<noscript>` on `/` is a list of every language, so a visitor without scripting can still choose one.
- `sitemap.xml` states `lastmod` from the commit (`src/lib/seo/build-date.ts`), not the build clock: a rebuild that changes nothing must repeat the same date, or a search engine stops treating the value as meaningful. `scripts/sitemap-split.mjs` then divides the single file Next writes into one per language and writes an index over them, so Search Console reports coverage for each language separately instead of one averaged number. The script checks the total before writing anything, so a mistake leaves the single-file sitemap in place rather than publishing a broken one.
- **A page's own content reaches a crawler only if nothing on it reads the router's search params.** Next renders a page on the server only up to the nearest Suspense boundary above a component using `useSearchParams`, and a route-level `loading.tsx` already provides such a boundary — so one such hook anywhere in the page tree replaces that page's entire body with its loading spinner in the HTML. The home page, the nine category pages and all 100 tool pages were serving a spinner as their whole `main` for this reason, and looked perfectly normal in a browser, which is how it went unnoticed. Where a page needs something out of the address bar, `src/lib/navigation/address.ts` reads `window.location` through `useSyncExternalStore` and answers `null` on the server instead, so the first client render matches what was prerendered. `src/lib/seo/prerender-policy.test.ts` fails if a search-param hook appears anywhere but the shell's own scroll restoration, which sits in a boundary of its own with a `null` fallback.
- A tool page reads heading, tool, then guide. `ToolIntro` renders the tool's name as the page's only `h1`, with its description and its category as the back control; `ToolPageClient` renders the interactive view, deliberately on the client because it needs a browser to do anything at all; `ToolGuide` renders from the server the neighbouring tools in the same section and the three questions a visitor actually arrives with, reusing wording the How page already carries in every language rather than translating new claims thirty times. Related links are plain addresses with no query, so a crawler follows them normally, and the suggestion rotates with the page's place in its section so the first few tools do not collect every inbound link while the rest are never offered. `ToolShell` wraps only a tool's own controls and renders no heading, since all 94 tools go through it and the route owns the heading. Each tool page also declares itself a `SoftwareApplication` in schema.org's own vocabulary, so the catalogue reads as software and not only as pages.
- **An address that does not exist is answered with Kit’s own page.** Until now the export served Next’s built-in not-found — “404 This page could not be found.” — which carried the site’s stylesheet but none of its design, in one language. `src/app/not-found.tsx` renders the document a host serves for any missing address. It brings its own `<html>` and `<body>`, because the root layout is a pass-through and every other route is given those by the layout of its language — and a missing address has no language. Nothing is fetched and nothing hydrates: a visitor reaches it because a link, a bookmark or a typed address has already failed. It shows the mark, the status, what happened, and one way home, through the same card the in-app not-found shows (`NotFoundCard`, shared with `app/[locale]/not-found.tsx`). One static file answers every address, so the wording for all 31 path locales travels inside the document (`src/lib/i18n/not-found-copy.ts`, keyed by path segment so the `/zh/` alias needs no special case) and `public/boot/not-found.js` swaps it for the language the address named, sets the title, and points the way back at that language — before the first paint, with the default language what is rendered, so the page is complete without scripting. It is `noindex` (Next marks the not-found route; the document states no canonical, so it cannot claim the home page as itself) and `404/index.html` is written alongside `404.html` for hosts that ask for it.
- The worker is what makes that page reach a returning visitor. `isUsableHtml` requires `res.ok`, so before this a device with the worker installed was answered out of its cache — last home or the shell — and shown an address it had not asked for; `isMissingPage` now passes the host’s own 404 through (`public/sw.js`). Offline behaviour is untouched: a fetch that fails still falls back to the cache and still lands on last home, and a 404 is never stored, because an address can start existing again.
- Pure engines and tests under `src/lib/`; client tool views under `src/components/tools/`; favorites and metadata-only history in Zustand stores.
- **A tool page says what it does in a sentence of its own, in all thirty languages.** `tools.<id>.description` is the card copy in the home grid *and* the string the tool search matches against, so it has to stay short enough to sit under a name in a grid — which made it the page's own first paragraph and its meta description too, at a median of 53 characters. `tools.<id>.summary` carries the page's sentence instead: 94 of them in English, each 105–160 characters, read on the server and handed to `ToolIntro` as a prop so it does not ride along in the payload of every page that only needs cards. It feeds the paragraph under the `h1`, the meta description and the page's structured data, which is where `scripts/discovery.mjs` reads from, so `api/tools.json` and `llms-full.txt` improved without being touched. A language without a summary falls back to its own translated `description`, never to the English sentence: `optionalKey` in `src/lib/i18n/catalogs.test.ts` exempts `^tools\.[^.]+\.summary$` from the key-parity rule, and the "either every sentence or none" rule keeps a language whole. **All thirty now carry all 94**, written against each catalog's own voice rather than turned from the English — "Draait alleen in je browser", "Körs bara i din webbläsare", "處理是ブラウザ內のみ", "在本機生成强密碼" — with the byte, hertz, kelvin and squared-unit vocabulary differing per language as it should (Taiwan's 公分/公尺/公克 beside 厘米/米/克).
- **The converter's unit dictionary is named in every language too.** `tools.everyday-converter.unit*` is 122 labels, and five catalogs had the whole set in English while others had 30–115 stragglers — an English plural `-s` German and Italian do not have ("Watts", "Volts", "Ohms"), an English spelling where the language has its own word (Spanish "vatios", French "kibioctets"), and whole families left behind (Dutch and Danish had 115 of 122). All 30 are named except where the language genuinely writes the unit the same way: kelvin, celsius, fahrenheit, bar, psi, hertz and its three multiples, stone and the CSS units `rem` and `em` in all of them, plus spelled-alike words such as Dutch "kilometer", Portuguese "megabytes" and French "volts". `catalogs.test.ts` records how many labels remain identical per language and fails if a language gets worse, so a new unit cannot arrive in English by default; the expected direction is a lower number.
- A sentence is measured in **columns, not characters** — a CJK glyph is about twice as wide as a Latin one, so fifty characters of Chinese and a hundred of English take the same room in a search result. `catalogs.test.ts` holds every present summary to 40–175 columns and at least 18 characters, which rejects a label by a wide margin ("From Hz to RPM", "Hz 到 RPM") and never a real sentence.

- Canonical production site: `https://trykit.pages.dev`; GitHub Pages backup: `https://TGthms.github.io/kit/`.
- PWA caches carry the build's stamp: `kit-shell-<build>` and `kit-rsc-<build>`, the second so a `.txt` body can never paint as the page. The stamp is a digest of the content the build ships, computed by `scripts/sw-precache.mjs` and written into the exported `out/sw.js` over the `__KIT_BUILD__` placeholder that `public/sw.js` keeps. Naming the caches after the content is what stops a device answering from an older release: a new build changes the worker's own bytes, so the browser installs it, it opens a fresh pair of caches, and activating it deletes the previous pair. Nothing written by an earlier build survives to be served, and the Offline access counts describe this build rather than merely "something is here" — before this, a device that had downloaded everything under an older release kept serving it while the page reported the new release as ready. The stamp moves only when the shipped bytes move, so a rebuild that changes nothing does not throw away what a device holds. The worker never returns a redirect `Response` or a `fetch()` result with `redirected: true` (Safari: “Response served by service worker has redirections”). Document navigations to `.txt` fetch the HTML route instead. Cached HTML for the exact URL is returned immediately; a hung first-time navigate fetch falls back at 400ms (exact cache) / 8s (last-home). In-app clicks use cached `index.txt` so they stay in the tab after idle instead of becoming a full document load. After first paint the worker silently fills the app's own pages (HTML and their payloads) for the locale in use before the shell's scripts and styles, because the fill pauses on pointer/key/wheel and whenever the tab is visible: a visitor who loses the network after a few seconds should still be able to open History, Favorites, the category pages and Offline access itself, rather than only the pages they happened to visit. It then fills the locale's tools, the compatibility addresses, and — on an unmetered connection — every other language plus pdf.js/FFmpeg. Fills use low-priority fetches. On Save-Data or a slow (2G) connection the worker prefetches only the language in use, skipping the other languages and the FFmpeg engine. This is full offline for the language you have open, not a 30-locale download of every tool on first visit.
- With the network off, an in-app click is a route change whenever the destination is held — both the document and the `index.txt` payload its route asks for — so the tab bar keeps its glide and no document is reloaded. Only a destination the device does not hold becomes a document load, which the worker answers from its cache (or with the last home it has). `src/lib/pwa/offline-navigation.ts` owns that decision, and the probe is deliberately generous: a miss is not an error, it falls back to the load.
- The Offline access page separates choosing from removing. Choosing is three pickers — the app's own pages, languages, and tools grouped by category — where each row holds one control and every picker has its own Select all and Clear. The pages are a download like anything else and all start ticked, including `/settings/offline/` itself, so the app can be prepared for offline use on its own without taking any tool. Every tool category starts closed. Removing has its own menu, closed until asked for, which lists only what is on the device (so it stays short however much the app offers), lets any combination of languages, tools and the media engines be ticked, names the count on the button, and offers every saved item from one control. It reports what the device actually holds, counted from the cache keys rather than by probing several thousand addresses: per language (complete or partway), per tool (reachable in how many of the languages that have anything), and for the media engines. Removing the app's own scripts, styles and icons is deliberately not offered — those are the application rather than something chosen on that page, and dropping them would leave the app unable to open its own pages. A language counts only languages the page can offer: addresses kept so an old link still resolves — a renamed tool, or `/zh/` — are prefetched but never counted, because nothing on the page can select them and counting them would leave every language permanently short of complete. `scripts/sw-precache.mjs` works both out from the export itself — an alias is a page whose own canonical names some other address, which is the same rule the language aliases use — rather than from a second list to keep in step, groups each language's pages under the ids the page offers (`pagesByLocale`), and offers only the pages the build actually wrote. That rule matters on the backup host, where every page is asked not to be indexed so it cannot compete with the canonical host: judging an alias by its "do not index" marker, as this used to, would have made every tool an alias there and left its Offline access page offering none. Removal reaches the compatibility addresses too, so removing everything leaves nothing behind.
- A language counts as ready only when its pages *and* their navigation payloads are all stored, so a download brings the payload for every page it takes. Taking only the payloads of tool pages would leave the chrome and category pages of a chosen language without theirs, and since the background fill covers only the language in use, a second language would never reach ready on its own.
- A download the visitor asked for fetches several resources at once (`OFFLINE_CONCURRENCY`), because they are waiting on the page and watching the bar. The optional background fill stays strictly one at a time, so it never competes for bandwidth with what someone is looking at.
- What was downloaded is recorded on the device (`kit-offline-plan` in localStorage, alongside the release it was fetched for), not inside the cache — a new release replaces the cache and would take the record with it, which is exactly when it becomes useful. When the record names an older release, or the cache has rolled past it, the page says so and re-runs the same selection in one tap. Nothing downloads without a tap. Removing everything forgets the record, so a visitor who declined the content is not asked for it again.
- After a deploy, a tab that still names deleted hashed chunks reloads once (`ChunkLoadError` / failed dynamic import). Retry on the error screen does the same. A 10s guard stops a reload loop.
- Locale documents bake `lang` and `dir` on `<html>` (`/ar/` is `lang="ar" dir="rtl"`). `/` stays an English LocaleGate. The boot locale-lang script remains a backup (`zh` → `zh-Hans`).
